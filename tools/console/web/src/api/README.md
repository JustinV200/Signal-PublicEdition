# api

Everything that talks to the console backend (`tools/console/src`) lives here, so a contract change touches one folder.

- `types.ts`: wire types for `/api/state` (including `openCommand`, the full `console open` line), SSE events (including `tasks`), send, action, `/api/devices`, `/api/away` and `/api/health` (`ConsoleCheck`: `{id, name, level, state, words, fix, command}`, with `TURN_HOOK_CHECK` and `SESSION_HOOK_CHECK`, the ids other views word).
- `parse.ts`: shape checks on every payload before it reaches the store (`parseConsoleHealth` for `/api/health`: a row without an id is dropped, an unknown level reads as `attention`, a null fix or command as `""`); `parseTasks.ts` (the `tasks` event) and `parseDevices.ts` (devices and away) beside it, sharing the field checks in `parseFields.ts`.
- `token.ts`: the per-login token (memory plus `sessionStorage`) and the `X-Console-Token` header.
- `client.ts`: `login` (stores the token), `getState`, `sendText`, `sendAction`, `getDevices`, `getHealth` (the console's own checks), `setAway` (the owner's own Away/Here toggle), `pickModel`; same-origin JSON; a 401 clears the token and throws `UnauthorizedError`, whose `message` is the server's reason and `openCommand` its `console open` line (both from the 401 body; with no reason in it, `NOT_SIGNED_IN`, the guard's `not signed in`, which the reducer and the signed-out page also read). The streamed requests (the event stream, the camera, setup runs) use `rejectUnauthorized`, which skips the body since their 401 is always `not signed in`. Every request, those three included (`fetchOrExplain`), fails with `the console server isn't answering` when it never reaches the server, not the browser's `Failed to fetch`.
- `sse.ts`: a `text/event-stream` parser for streams read with fetch.
- `events.ts`: `connectEvents(handlers)` reads `/api/events` with streaming fetch (EventSource cannot send headers), reconnects with 1/2/4/8 s backoff, and re-fetches `/api/state` before each reopen so a dead token becomes `onUnauthorized`. A stream with no bytes for `STALL_MS` (20 s; the server's keepalive is every 5 s) counts as dead and is reopened, and `onAlive` fires on every chunk. `isStreamStale(syncedAt, now)` applies the same 20 s to the last byte the page saw, for the status line's `no update for 25s` and the scope's `NO SIGNAL 25s`. It returns `{resync, close}`: `resync()` drops the stream and reconnects at once.
- `camera/stream.ts`: `openCameraStream({onFrame, onError, onEnd})` reads `/api/camera/stream` with the page's token (the server adds the whiteboard's, so the page never holds it) and hands out each frame as a `blob:` URL; the returned function aborts the fetch, which ends the stream upstream. `camera/mjpeg.ts`: `createMjpegParser()` cuts the multipart body into JPEGs by each part's Content-Length.

Public API: `index.ts`. Depends on nothing else in `src/`.

`setup/` is the setup wizard's and System's tools list's side: `runSetup(request, onLine)` posts one fixed command to `/api/setup/run` and reads its NDJSON answer as it streams (`{"line"}` per output line, then `{"exit"}`); `openSetupTerminal(tool, step)` posts `/api/setup/terminal`, which opens a terminal on that one step. A 409, or the stream's `{"busy": true}` record when a command loses the race after the server's check, rejects with `SetupBusyError`, which the wizard words as busy, not failed. `parseAutoStops` reads where `setup auto` stopped. `types.ts` mirrors the setup CLI's requests and answers (a tool's health row has `words`, `fix` and `command`, as the console's checks do), `parse.ts` checks them, and `jsonDocs.ts` pulls the CLI's indented JSON documents out of its output lines (a step may print a program's own lines first); `outputParts` keeps those lines in order around each document, for the wizard's readable log.
