# views/setup

The setup wizard (`Ctrl+9`, `Open setup` in System and in Commands, and where `setup` / `/setup` open the console with `#v=setup`). Its tab shows only while a picked tool is unfinished or Setup is open: `useSetupTab` (used by the shell) reads `setup list` at sign-in, again when Setup opens or closes, and on Refresh, and `wizardScreens.ts`'s `showsSetupTab` is the rule (picks not read yet, or the first read failed, hide the tab; a later failure keeps the last answer). Every action runs one fixed command of the setup CLI (`tools/setup`) through `POST /api/setup/run`, so the registry, settings schemas and `.setup/progress.json` stay the single source of truth, and the wizard resumes at the first unfinished tool.

- `SetupView.tsx`: the header (`page 4 of 16`, or `couldn't read your setup: see below` when `setup list` fails, never `loading…` beside the error), the strip, one page at a time ("pages", so "step" only means a step row), the picked tools beside a tool page, and Back and Next only on the pages whose primary button doesn't lead on to the next page (a tool page, the Tour; the others' primary does, Summary's is `Open Chat`). Which page is open (`useStartScreen.ts`, `wizardScreens`' `openIndex`): the one kept in the store (`setupPage`, by `screenKey`), so leaving Setup and coming back lands on it; else, on a first visit or when that page is gone, where setup stopped (`wizardScreens.ts`: built from `setup list`, resumed from progress, or opened at a tool by a System tools row or `#t=`), which is then kept too, so finishing a step never moves the wizard. The picks are `setup list`'s `picked` (progress `chosen`), not a status, so a fresh checkout whose console the window already built still opens on Welcome. It re-reads `setup list` whenever the window gets focus back (a step finished in a terminal shows on return). It holds the one `Add to Claude Code` runner (`run/useAddToClaude.ts`) its screens share, so Summary knows a wire worked.
- `head/`: `WizardStrip` (`Welcome › Pick › Tools 3 of 7 ✓ › Connect › Summary`, from `stripSections`: one section per run of pages, Tools counting the done picks and opening the first unfinished one, the Tour page under Summary), `ToolList` (the picked tools beside a tool page, each a button with its state as a shape and in words in its name and tooltip) and `wizardHead.module.css` (the header's running note, the strip, the page-and-list grid; the rest of the wizard and the health list share `setup.module.css`).
- `useSetupDraft.ts`: one field's typed text held in the store (`setupDrafts`), used by a value step, the settings form (by its own keys; it reopens by itself when it holds typed values) and the samples panel, so typing outlasts leaving Setup. `usePicksToStore.ts`: puts the picks from each `setup list` read (the Setup tab's and the wizard's) in the store for the console tour.
- `screens/`: Welcome (intro and missing programs, a URL in where to get one a link via `markdown`'s `LinkedText`, as on a tool page), Pick tools (`PickRow` per tool under its group, from `pickGroups.ts`; cost tags, Pick all / None, `Add Gmail too`; `Save N picks and install` runs `setup choose` then `setup auto`; the Task console is ticked before any pick), one page per picked tool (with `Run the automatic steps` while one is left, a `Set up, not added to Claude Code yet` banner and `Add to Claude Code` while a finished tool isn't wired), Permissions (`setup plan` split at its blank line: one plain line per tool on what Claude may do without asking, then the exact entries under a collapsed `Show exact entries` (`consentPlan.ts` splits it; a plan that exits non-zero shows as `✗ Couldn't read what setup will add: …`, never as consent); then `Add to Claude Code` runs `setup wire --yes`; it stays put with the restart line and `Next: check everything`, and, when the console is picked, links Claude Code with the claim sentence), Summary (the restart line again, then health of the picks) and Tour (the console tour button and GUIDE.md a section at a time).
- `steps/`: a step's status (mark and word) and its controls by kind: Run, Yes/No (e.g. browser auto-approve), Mark done, a value field, the settings form, the samples panel, or, for steps that take a secret, Open a terminal (a PowerShell window on `setup.ps1 step <tool> <step>`: just that step, no wiring, the secret typed there; off while another step runs) and Check again, which re-reads `setup list` and says what it found and when (there's no Mark done: the status is only what setup saved). The console's claim step is `ClaimLink`: the link state in words, the claim sentence with Copy, and a self-tick (`setup mark console claim done`) once a session links (a busy answer or an exit 3 reads one `!`, not a cross). `StepGuide`: a step that names a guide (its registry `doc`) shows `Guide: <file>`, collapsed; opening it reads `setup doc <tool> <step>` and renders it with `markdown`'s `Markdown`, or the CLI's sentence when this copy lacks the file.
- `settings/`: forms rendered from the settings schema (`setup config <tool> --list`), saved with `--set`; placeholders are flagged in words.
- `samples/`: copytone samples by paste, file paths or sent mail.
- `run/`: `useSetupRun` (one command with live output; `button(key)` gives each of a control's buttons its look), `runningState.tsx` (`RunningProvider`, which `SetupView` wraps the wizard in, and the pure `claim` / `release` / `buttonLook` rules: one command at a time, a claim only takes a free state and only its holder releases it, only the clicked button reads Working…, the rest are off with `another step is running`; outside it, as in System's tools list, each runner has its own), `OutputLog` (a 409 reads `! busy` and is never handed to Claude; a batch's needs-you points at the stop rows below; the hand-off gets the raw lines), `readableLog.ts` (what the log shows: program lines as they are and each JSON document as its words, never the JSON, not even part-way through streaming in or cut short; exit 3 as `! needs you: <the last document's first message>`, or a bare `! needs you` when nothing shows), the header's `role="status"` line while any command runs (`RUNNING_NOTE`, since the disabled buttons can't be focused to give their reason), the Pick screen's batch runner (held by `SetupView`, so its log survives screen changes), `AutoStops` (where `setup auto` stopped, from its closing JSON), `HandToClaude` (sends a failure to Claude while a session is linked and stays on Setup, saying "Sent. Claude answers in Claude Code."; otherwise `ui`'s `CopyButton` copies it, noted "not linked to a Claude Code session yet"), `useAddToClaude` (runs `setup wire`) and `AddResult` (its log, then the restart line).
- `health/`: health in words and its list, shared by System's CONSOLE and TOOLS groups and the Summary screen. `HealthList` renders `HealthItem`s (`toolItem` from `setup status --json`, `consoleItem` from `GET /api/health`): a mark, the name, a bold state word and the check's words, the row's button (the caller's `renderAction`), and under them `HealthFix`, the fix in words and the exact command with Copy. Each row has an element id (`healthRowId`) and takes focus, so System's Models pointer can land on it. `ToolHealthList` adds a tool's button: a finished tool whose servers and hooks aren't in Claude Code's config (`wired` false) reads `◐ Set up, not added to Claude Code yet` with `Add to Claude Code`, never Active; a `Down` row's `Fix` opens its tool page with the check (`setupCheck`), which `CheckBanner` puts at the top, so a page whose steps all read done says why it opened. Console checks read `● OK`, `◐ Needs a look`, `✗ Not working`. The marks are `ui`'s SVG shapes, like every mark in the wizard: step status, run results, the claim link, the strip's `▸` and `✓`; `health.module.css` styles the rows and the banner.
- `useSetupQuery.ts`: read-only commands (list, intro, plan, tour, status, doc) loaded on open and on Refresh; `parse` gets the lines and the exit code.

Public API: `index.ts`. Depends on `api`, `state`, `ui` and `markdown`.
