# Signal console

A local web app that fronts the owner's Claude Code **orchestrator session**. Whatever the owner types goes to the orchestrator as a plain-language request, and the orchestrator does the work with its own tools. Otherwise the console *reads* status on its own: the voice hub, the whiteboard, the devices, the task list and whether the orchestrator is busy.

**The owner's own clicks act directly**, without the orchestrator. They run only on the owner's click in the logged-in page (token and origin checks), never on a message or an agent's request:

- **The buttons** (voice Start/Stop, board Send to projector, to-do list, idle board, Show live version, Show saved copy, Realign, Full calibrate). `POST /api/action` runs each one in the server, deterministically, from a fixed list: voice through the same code as `console hub start|stop`, the board through the `whiteboard` CLI with fixed arguments (see `src/signal_console/actions/README.md`). The result shows on the action's row in the feed. A failure there is plain words, what failed and what to do (`Couldn't stop Voice. Try Stop voice again.`); pids and log paths go to the server's log instead. A save name shows as typed, in quotes (`Send to projector: "lecture"`), with hidden characters escaped.
- **The Away/Here toggle** in the page's System tab. `POST /api/away` turns the brief's away mode on or off directly (`signal_brief.away_on`/`away_off`, the same as `brief away on|off`), without asking the orchestrator. The `state` snapshot carries the same away block (`{state: here|away|asleep, endsAt, note}`, `asleep` from sleep mode), so the page's title row shows Away or Asleep on every tab.
- **The setup window** (the Setup tab and System's Tools list). `POST /api/setup/run` runs one command of the setup CLI (`tools/setup`) from a fixed list and streams its output; `POST /api/setup/terminal` opens a PowerShell window on `setup.ps1 step <tool> <step>` (that one step, no wiring) for steps that take a secret. See `src/signal_console/setup_cli/README.md`.
- **The model strip's pickers** (in the page's System tab). `POST /api/models` writes two allowlisted settings keys, `model` and `effortLevel`, in `.claude/settings.local.json` (for every new Signal session), and voice's `tools/audiohub/.cache/brain-choice.json`. Nothing else, and only values from fixed lists (see Security).

The camera view is a read like the other status reads: it shows the webcam and changes nothing.

- `src/signal_console/`: the Python backend (HTTP server, CLI, hooks). This README covers it.
- `web/`: the React/TypeScript frontend, built to `web/dist/` and served by the backend. It has its own docs.

## Setup

Run `.\setup.cmd` at the repo root. To redo only the console: `.\setup.cmd console`.

**Start at logon (optional setup step).** The console's `logon` step runs `register.ps1 -Port <port>` (the port setup stores from `.\setup.cmd --port N` and keeps for later runs, 8790 until one is given). It registers, for the current user and not elevated, a logon task that runs `uvw run --project tools\console --frozen --no-sync pythonw -m signal_console serve --port <port>` with no window, and a Start-menu shortcut that runs the same with `open --port <port>`. A logon-task server that can't start (say the port is taken) writes why to `.state/server.log` and exits 1, which shows as the task's last result in Task Scheduler. pythonw has no console, so when the shortcut runs `open`, what `open` would print (its progress and why it failed) goes to `.state/server.log` too, next to the log of the server it starts. Both are named `Signal console (<checkout folder>, port <port>)`, so a second checkout registers its own pair instead of replacing this one's; each checkout's console needs its own port. One checkout has one registration: running the step again after `.\setup.cmd --port N` replaces this checkout's registration on its old port (deletes its task and shortcut) and prints a line saying so, since two task servers of one checkout would share `.state/` and the second would strand the first. It leaves the old port's running server alone, since that server may be serving the setup wizard that runs the step, and says so: the old server runs until it's closed or you log off, and from the next logon only the new port's starts. The script refuses when another program, such as another checkout's console, listens on the port (it reads the socket table and the holder's paths, and never connects), and when a same-named task or shortcut opens another checkout's console (its arguments must name this checkout's quoted `tools\console` path); `unregister.ps1` refuses those too and touches neither. The server starts at the next logon, not now. `unregister.ps1 -Port <port>` stops this checkout's server on that port and removes the task and the shortcut. Both scripts share their naming and "is this checkout's" rules through `registration.ps1`. Skipping the step registers nothing.

## Each new session

Nothing to do by hand. A new Claude Code session's first `console tasks set` (AGENTS.md section 3) takes over a closed claim, and the feed shows a note saying where requests now go. If the wrong session took it, run `console claim` in the right session to take it back. Any top-level session that follows AGENTS.md section 3 (a headless or job-runner one too) can take a closed claim this way, and since a live claim is never replaced automatically, it then keeps it until `console claim` moves it. Details under "How it talks to the orchestrator".

## If it breaks

`console X` below is `uv run --project tools/console --frozen --no-sync console X`, run from the repo root (the page and `console doctor` print the full line with this checkout's path). Start with `console doctor`: it lists every check that isn't ok with its fix.

| Symptom | Cause | Run |
| --- | --- | --- |
| `console open` stops with "the console's page isn't built yet", or the window shows that page | `web/dist` is missing. `open` never builds; setup does. | `.\setup.cmd console`, then `console open` |
| `console open` says the port "is held by the console of another checkout" (or another program) | Two checkouts both default to 8790, and the other one's server holds it. | Stop that console, or `console open --port <a free port>`; for the logon task too, `.\setup.cmd --port <a free port>` and run the `logon` step again |
| `console open` says the server "stopped at once" and quotes a log line | The server couldn't start; the line says why (a `bind` error means the port is taken). | Fix what the line names; for a taken port, `console open --port <a free port>` |
| `console open` says the server "didn't start within 15 s" | A slow first start, or a hang. | Read `tools/console/.state/server.log`, then `console open` again |
| The setup window drops to the terminal | The line above the fallback says why: a missing program, a failed build, or who holds the port. | What that line says, e.g. `.\setup.cmd --port <a free port>` |
| Nothing opens from the Start-menu shortcut, or the server isn't up after logon | Under pythonw nothing can print, so the reason is in the log. | Read `tools/console/.state/server.log`, then `console doctor` |
| The page reads `Claude session closed` and Send is off | The claimed session closed. | `console claim` in the session to use (or its next `console tasks set`) |
| Claude's status stays `state unknown`, or replies never show | The turn hook is missing or failing (the status line then reads `state unknown · turn hook missing`, and System's Console group has the row). | `console doctor`, then `.\setup.cmd console` if a hook row fails |
| The page is signed out | Its login key expired or was used, or the session digests were cleared. | `console open` (the page shows the full line with Copy) |

## CLI

| Command | What it does |
| --- | --- |

| `console open [--port 8790] [--view V] [--tool T]` | Start the server if needed (detached, log in `.state/server.log`), then open `msedge --app=http://127.0.0.1:<port>/#k=<key>` (or the default browser without Edge). `--view setup --tool mail` opens on the setup wizard at that tool (`&v=setup&t=mail`); `setup` and `/setup` use it. It never builds: without `web/dist/index.html` it stops at once and prints `.\setup.cmd console`. It prints `Starting the console server...`, and if the server exits during the wait it prints the last line of `server.log` (with the `--port` way out on a bind error). Then it prints every `console doctor` row that isn't ok. Under pythonw (the Start-menu shortcut) all of that goes to `server.log`. |
| `console claim [--label NAME]` | Make the calling Claude Code session the orchestrator. Run it from that session's own Bash or PowerShell tool: Claude Code gives each session's tools its inbox address and token (`CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`), and `claim` saves them to `.state/orchestrator.json`, readable only by you. It replaces any claim, live or not. Without `--label` the label is the local time of the claim (`Tue 17 Nov 10:25`), so sessions read apart. A successor orchestrator (after a handoff) runs it again, though its first `tasks set` also takes over a closed claim (below). |
| `console hub start\|stop\|status` | Start the voice hub detached (`uv run --env-file .env --project tools/audiohub --frozen --no-sync audiohub run` from the repo root, output in `.state/hub.log`), stop it, or report. `start` refuses if a hub is already running. `stop` stops the hub it started, or else the one named in the hub's own record (`tools/audiohub/.cache/hub.json`, which every `audiohub run` writes), so a hub started in a terminal stops too. It asks the hub to shut down cleanly first (over its kernel IPC, so the music is restored), and kills it only if it hasn't exited after 10 s. A kill takes only the hub's own processes; daemons that its MCP servers started keep running. |
| `console doctor` | Check the console's setup: one line per row (`ok`, `attention` or `FAIL`, then what was found, then `Fix:` and `Run:` when not ok). Rows: server, port (another checkout's console on it, named from the listening process), built page, Claude session (linked, open, age), turn hook (4 events) and session hook (2) in either settings file, a hook in both files, the last hook report, `hook.log` errors in the last 24 hours, Edge, whiteboard, and errors in `hub.log`. Read-only, works with the server down; exits 1 only on a FAIL row (page not built, a hook entry missing, no Edge). `--summary-json` then ends with the first FAIL row as one JSON line, `{words, fix, command}`: the setup tool's verify check runs this (`tools/setup/README.md`, Verify checks). See `src/signal_console/health/README.md`. |
| `console tasks set ID [--name N] [--pct P] [--status S] [--next T] [--you T]` | Create a task or change only the fields given (a new one needs `--name` and starts `queued` at 0%). `--status` is `review`, `building`, `needs_you` (needs `--you`), `queued` or `done`. Checked by `signal_tasks`: id is lowercase letters, digits, `-` and `.`; pct 0-100; one-line text. After saving, it claims the console for the calling session when the claim is missing or its session has closed (see below). |
| `console tasks done ID` / `rm ID` / `show` | Mark done (100%), delete, or print the list in display order. |

The console's voice buttons run the same code as `hub start` and `hub stop` in the server. The orchestrator runs `tasks set` whenever a task changes state (AGENTS.md section 3). For example:

```
uv run --project tools/console --frozen --no-sync console tasks set brief-p2 --name "Brief phase 2" --pct 60 --status review --next "fresh reviewer on the hub diff"
uv run --project tools/console --frozen --no-sync console tasks set brief-p2 --status needs_you --you "say yes to the hook"
uv run --project tools/console --frozen --no-sync console tasks done brief-p2
```

## How it talks to the orchestrator

**Sending** goes through the shared `signal_orchestrator` package (`packages/orchestrator`), which the voice hub's hand-off uses too, over Claude Code's cross-session inbox (a named pipe), [documented here](https://code.claude.com/docs/en/cross-session-messaging#the-sessions-inbox-socket). The first line is the documented auth line, `{"type":"auth","token":"<token>"}`. Because it carries the session's own token, Claude Code counts the message as coming from the session's own child, so it delivers the message even though the orchestrator runs with bypassPermissions.

The message line, `{"type":"user","message":{"role":"user","content":"<text>"}}`, is **not documented**. It's the frame Claude Code's own sender writes, taken from the source of `claude.exe` 2.1.301 and confirmed with a probe. It's an internal format and may change in a later Claude Code version. If sends report `failed`, or say `sent` but never arrive, check this first (`inbox.py` in `packages/orchestrator`). The sender reports `failed` when the pipe can't be opened, or when Claude Code closes the connection straight away (which is what happens when the token is wrong).

Every message starts with `[Signal console] <name>: ...`, because the inbox doesn't show the sender's name. `<name>` is `SIGNAL_OWNER_NAME` from the repo-root `.env` (quotes optional), or `the owner` when the file or the key is missing. The console reads only that key, once per process (`owner.py`), so restart the server after changing it. Buttons send nothing to the orchestrator.

**The marker is a label only, never consent.** Any process that holds the session's inbox token (anything the session itself runs, for one) can write the same words. The orchestrator should weigh a marked message on its content, the same as any other.

**The voice hub sends here too.** When the voice agent gets a job beyond its quick tools (code, settings, anything complicated), it reads the same claim file and sends one message starting with `[Signal voice]`, straight away and without a spoken question. The message quotes the owner's recent words as the hub transcribed them, apart from the voice agent's summary, and asks the orchestrator to treat a summary that doesn't match them as suspect. That marker is a label only too. The hand-off message itself doesn't show in the console's feed, though the orchestrator's reply does (through the turn hook). See `tools/audiohub/src/audiohub/brain/handoff_tool/README.md`.

When the claim changes (a different session or label, or the claim found when the server starts), the feed shows a `note` event saying where messages now go and how long ago that session was linked (`Messages now go to the session labelled "Tue 17 Nov 10:25" (linked 3 hours ago).`), so a claim the owner didn't make is visible.

**A new session takes over a closed claim by itself.** `console tasks set`, which every orchestrator runs as it starts a task (AGENTS.md section 3), claims the console for its caller when there is no claim or the claimed session has closed (the liveness check below), through the same claim writer as `console claim`, so the takeover shows as a note too. A live claim is never replaced this way, nor one whose session can't be checked (the pipe list can't be read); only `console claim` does that. If the task saves but the claim can't be written, `tasks set` says so and exits 1; run `console claim` to retry. Run without the inbox variables (a plain terminal), `tasks set` claims nothing. Subagents run inside their parent's Claude Code process and their tools get its inbox variables, so a subagent's `tasks set` claims for its parent session, never for itself. Nothing claims at SessionStart. The cost: any top-level session that runs `tasks set` (a headless or job-runner one too) can take a closed claim and then keeps it; the note shows it, and `console claim` in the right session undoes it.

The server also checks, each poll, that the claimed session is still open: its inbox pipe must be listed under `\\.\pipe\` (a name lookup, no connection, so nothing reaches the session). The page gets only `orchestrator.alive`, a boolean, and `orchestrator.claimedAt` (the claim time, for the tooltip's age), never the socket name or token. A closed one reads `Claude session closed` and Send is off until a new session runs `console claim` or `console tasks set`.

**Replies and the busy status** come from the turn hook, which POSTs each event to `/api/hook/turn`:

- `UserPromptSubmit` starts a turn. It also fires on turns Claude Code starts by itself (a background agent finishing, an inbox message), so those show too.
- `Stop` ends it, with `last_assistant_message` (shown as Claude's reply) and the count of `background_tasks`. `StopFailure` (an API error) ends it too.
- `Notification` `idle_prompt` ends a turn, but only one whose start is at least 60 s older than it: a late idle prompt from the last turn can't end an inbox turn.

Each report carries `at`, stamped when the hook process started. Async hooks can land out of order, so a start and an end within 2 s of each other count as one turn; that fails towards `idle`, and the next hook corrects it. Interrupts fire no hook, so a turn with no hook (and no subagent change in `tools/usage/.state/usage.json`) for 10 minutes reads as stale. The states the page shows:

| State | When | Shows |
|---|---|---|
| working | a start, no end yet | `Claude · working 0:42` (+ ` · 5 agents`) |
| agents | no turn, but the session's subagents run | `Claude · waiting on 5 agents` |
| idle | no turn, no agents | `Claude · idle` |
| stale | working, no hook for 10 min | `Claude · quiet for 12 min (interrupted?)` |
| unknown | no hook since the server started | `Claude · state unknown until its next turn` |

Agents are the session's entries in `usage.json` seen in the last 2 hours. After a turn ends, that count is checked against Stop's `background_tasks`; when they disagree the lower one shows, with a `?`. A delivered request reads `sent` until the start hook arrives: the console never marks Claude busy by itself.

## Security

- Listens on 127.0.0.1 only. The `Host` header must be `127.0.0.1:<port>` or `localhost:<port>`, which blocks DNS rebinding.
- Any `Origin` header must be the server's own, and the page's non-GET requests must send one. No CORS headers are ever sent.
- Login: `console open` gets a one-time key (single use, valid 60 s) and puts it in the URL fragment. The page trades it at `/api/login` for a random session token (`{"token": ...}`). Each login mints a new token; the server keeps SHA-256 digests of the newest 8 (never a token) in `.state/session-digests.json` and loads them before its port opens, so an open page keeps working across a server restart with no new login. To sign every window out, stop the server, delete `.state/session-digests.json`, and start it again.
- All of `/api/*` needs that token in the `X-Console-Token` header (401 without it), compared in constant time, except `/api/login` and the local routes (`/api/hook/turn`, `/api/local/login-key`). Those take `.state/local-key` as `X-Console-Key`, also compared in constant time. The page reads the event stream with a streaming `fetch`, because `EventSource` can't send headers.
- There's no cookie on purpose: browsers send a 127.0.0.1 cookie to every port on 127.0.0.1, so any other local server would receive it. A header only goes where the page's own script sends it.
- A 401 body is `{error, openCommand}`: the reason (`not signed in`, or `that login key is wrong, used or expired`) and the full command line, `uv run --project "<this checkout's tools/console>" --frozen --no-sync console open` (`open_hint.py`), which the signed-out page shows with Copy. It holds no key or token, only this checkout's absolute path, and no CORS header is ever sent, so only local processes can read it. `/api/state` carries the same line, so the page can still show it while the server is down.
- The hook and the CLI send the local key (and the hook its reply) only to the port in `daemon.json`, and only while the process recorded there (pid and start time) still runs. A file left behind by a crashed server never sends them to whatever holds that port now.
- `GET /api/health` (token-guarded, read-only) returns the same rows as `console doctor`. Every check is a local read: no request is made, so the port check, which names whatever listens on this checkout's port, never sends the local key or a token to it. No row carries a socket name, key or token (the claim row gives only its label and age; hook and hub errors are counted, not quoted). It does carry local paths (this checkout's, another checkout's on the port, the log files), like the 401 body.
- Every response carries a strict CSP, `nosniff` and `no-referrer`. Request bodies are capped at 64 KB. Rejected connections are closed.
- The camera proxy (`GET /api/camera/stream`) sits behind the same token and origin checks. The server adds the whiteboard's `X-Signal-Token` itself; the page gets only the JPEG stream, never the token. The page shows frames as `blob:` images, the one addition to the CSP's `img-src`.
- The routes that change something without the orchestrator are `POST /api/action`, `POST /api/away`, `POST /api/models`, `POST /api/setup/run` and `POST /api/setup/terminal` (see the top). `/api/action` takes `{action, args?}`: the action must be one of the fixed seven, and its only free string, a save name, must be in the whiteboard's current save list. It's passed to the whiteboard CLI as one list argument after `--`, never through a shell. Voice actions share one lock and board actions another, so a second click while one runs gets 409 (no two hubs, no two calibrations). `/api/away` takes `{on: bool, until?: text}` (until is at most 40 characters, read by `signal_brief.parse_until`).
- `POST /api/setup/run` takes `{command, ...}`; `setup_cli.build_call` turns it into setup CLI arguments (a list, never a shell). The command name must be one of a fixed list, ids are checked by shape and can't start with `-`, and free text goes as `--flag=value` (one line), as `samples files` path arguments (one line, never empty or starting with `-`), or on stdin. The free-text fields are `apply`'s `value` and each `config` `set` value (at most 1000 characters; setting ids at most 200), the `samples files` paths (1 to 50, at most 500 characters each) and the `samples paste` text (on stdin, at most 60,000); `wire` takes no free text. The commands that write are `choose`, `auto` (every pick's automatic steps, or the named tools'), `mark`, `apply`, `config --set`, `wire` and `samples files`, `paste`, `mail` and `keep`; they run one at a time, so a second gets 409 (one that loses the race after that check streams its reason as `{"line", "busy": true}`, then exit 1), while read-only ones (`intro`, `list`, `status`, `plan`, `tour`, `prereqs`, `doc`, `config --list`, `samples count`) run beside them. `doc {tool, step}` prints a step's guide for the wizard: it takes the two shape-checked ids only, and the setup CLI opens just the file its registry names for that step, inside the repo. A page that closes mid-install doesn't stop the command. `POST /api/setup/terminal {tool, step}` starts only `powershell -NoExit -ExecutionPolicy Bypass -File setup.ps1 step <tool> <step>`, with shape-checked tool and step ids; the setup CLI refuses an id its registry lacks (exit 2) before running anything, and the step runs in that window with no wiring, so a secret typed there never reaches the page or the server.
- **What a page token can change through `/api/setup/run`.** The checks above limit how a request is shaped, not what it reaches. Anyone holding a page token can record setup progress (`choose`, and `mark` sets a step done or skipped); run any registry step that doesn't need the owner's own terminal (`apply`, or `auto` for the picks' required run and copy steps that aren't terminal steps or browser sign-ins; each with the step's fixed command from `tools/setup`'s `tools.json`: `uv sync`, `npm ci`, `docker build`, a PowerShell script that registers a scheduled task); set `.env` values (`apply --value` on such an env step); write the mail and calendar owner address into source (`apply --value` on the mail tool's address step, `SELF_ADDRESS` and `OWNER_EMAIL`); change any tool's settings (`config --set`: the tools' TOML configs and tracked files, including `AGENTS.md`, the `schedule.psd1` files and `life/areas/job-search/runbook.md`, re-running a step a changed setting names); and change Claude Code's config through `wire` (MCP servers in `.mcp.json`; allow rules, `enabledMcpjsonServers` and hooks in `.claude/settings.local.json`; `statusLine` in `~/.claude/settings.json`), taken from the registry for every tool progress marks done. Through `/api/setup/terminal` it can open a visible window that runs one registry step at once (the steps `apply` reaches, plus the terminal ones, which then wait there for the owner's password, Windows Hello or typed value). It can also read: `doc` prints a guide the registry names (the tools' READMEs and SETUP files, which may hold the owner's own addresses and paths), `samples files` reads any local file or folder path it's given and copies the text into the copytone skill's samples, and `samples mail` returns up to 25 of the owner's recent sent emails to the page. `wire --yes` is the owner's click on Add to Claude Code after the page has shown `setup plan`. Before `wire` changes one of its three files it copies the old one to `.setup/backups/`, and it refuses a file that isn't a JSON object (see `tools/setup/README.md`).
- `POST /api/models` takes `{target, field, index}`. The index points into a fixed server-side list (`signal_modelchoice`: the documented model aliases, and the efforts `low` to `xhigh`), never a free string. Orchestrator lists start with "use my user settings", which removes the key. The settings writer (`models/settings_writer.py`) only ever touches `model` and `effortLevel`; refuses a file that's missing or doesn't parse as a JSON object (it's never replaced with `{}`); copies the old bytes to `.state/settings.local.bak.json`; and re-reads the file just before the atomic write, writing only if it's unchanged (one retry, then it refuses). A Claude Code write landing between that re-read and the replace can still be lost; the backup covers it. The first write reformats the file (`indent=1`). `.claude/settings.local.json` now has a second writer, setup's `wire`, which re-reads it the same way before its own atomic write and keeps its own backup in `.setup/backups/settings.local.json`; the two share no lock, so the re-reads and the backups are what keep one from losing the other's change. The voice brain re-checks `brain-choice.json` against the same lists when it reads it.
- Static files: a path with a backslash, a colon, NUL, an absolute path or a `..` segment never reaches the filesystem; it gets `index.html`. Until `web/dist` is built, every page path gets a placeholder naming `.\setup.cmd console` with a Copy button; its script is served by the server itself at `/placeholder-copy.js`, since the CSP allows only the server's own scripts.
- `.state/` is locked to the current user every time it's ensured (each start), and the secret files are locked before anything is written to them. If a lock fails, the write fails too; for `session-digests.json` that means the digest isn't saved (a page login still works; it just won't survive a restart).

## State (`tools/console/.state/`, gitignored)

| File | What it holds |
| --- | --- |
| `daemon.json` | The running server's pid, start time and port. |
| `local-key` | The secret that the hook and CLI send. |
| `session-digests.json` | SHA-256 digests of the newest 8 page session tokens, never a token, so open pages survive a restart. |
| `orchestrator.json` | The claimed inbox: socket, token, label, claim time. The voice hub reads it for hand-offs. |
| `history.jsonl` | The last 200 message, delivery, voice and note events, replayed when a page connects. |
| `hub.json` | The pid and start time of the hub that `console hub start` launched. |
| `hub.log` | That hub's output, read for the phase and the voice feed. |
| `hub.prev.log` | The `hub.log` from before the last start, kept so a crashed hub's reason survives. |
| `server.log` | The server's log. `serve` writes it itself; a server `console open` started sends all its output there instead (and then adds no second writer). `console open` run under pythonw (the Start-menu shortcut) writes what it would print there too. |
| `hook.log` | Turn and session hook failures. |
| `session-models.json` | `{session_id: {model, at}}` for the 20 newest sessions, from the session hook; and its `.lock`. |
| `settings.local.bak.json` | `.claude/settings.local.json` as it was before the model strip's last write. |
| `models.lock` | Held while a model strip pick is written. |
| `tasks.json` | The orchestrator's task list (`console tasks`; format in `packages/tasks`), and `tasks.json.lock`. |

Voice phase and feed only work for a hub started by `console hub start`. For a hub started some other way, the console shows `running` with no phase (Stop still works on it). Hub lines written while the server was down never reach the feed.

## Layout

`actions/` (the buttons: checking a click, running it), `orchestrator/` (claim file, chat wording; the claim type and inbox sender come from `packages/orchestrator`), `status/` (hub probe and log parsing, whiteboard reader, device rows), `away/` (the Away/Here toggle), `hub/` (hub process control), `turns/` (the orchestrator's turn state), `models/` (the model strip: settings writer, session models, voice's pick), `server/` (aiohttp app, events, routes, security), `hooks/` (turn and session hooks), `setup_cli/` (the setup window's bridge to the setup CLI), `health/` (the console's own checks: `console doctor`, `/api/health`), `cli/`. Each has its own README.
