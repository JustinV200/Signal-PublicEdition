# setup

Signal's first-run setup. Standalone uv project, stdlib only (setup runs before anything else is installed).

- `setup.ps1` / `setup.sh` at the repo root check for uv and run `setup` here. On Windows people start it as `.\setup.cmd` (or a double-click), which runs `setup.ps1` past PowerShell's script policy.
- `.claude/skills/setup/SKILL.md` drives the same CLI from Claude Code; it only reasons when a step fails.
- The setup window (the Setup tab of `tools/console`) runs the same CLI from buttons through the console server, so the CLI stays the one source of truth for tools, steps, settings and progress.
- `src/signal_setup/data/tools.json` is the tool registry both use: each tool's platforms, prerequisites, steps, MCP servers, permission rules, hooks, verify check and its optional `fix`, plus its `evidence` (local paths that show it was set up on this machine; see Found already set up below), its `group` (Core, Everyday, Hardware, Extras) and `cost` (a few words: time, account, hardware) for the setup window's Pick page, and `consent`, one plain line on what Claude may do without asking once the tool is added (every tool with permissions, hooks or an `unattended_claude` step has one; a test holds this). A step marked `unattended_claude` (jobhunt's and mail-digest's `schedule`) registers a scheduled Claude run with tools, which acts with nobody asked. A step marked `opens_browser` (the mail and calendar sign-ins) needs the owner at the browser. Add a tool there, not in code.
- `src/signal_setup/data/intro.txt` is the intro paragraph (first screen and the top of the README; a test keeps them in step).

## Commands

| Command | What it does |
|---|---|
| `setup [--port N]` / `setup ui [tool] [--port N]` | The setup window: stores `N` (the console's port) as the `port` answer, or without `--port` uses the stored one (8790 when none is), prints one line per program it needs (uv, Node.js, Edge; a missing one with its `winget` command), installs and builds the console with its registry steps if needed (`1/3 Installing`, `2/3 Packages`, `3/3 Building`), then `console open --view setup --port N` (at one tool when given; a console server already running keeps its own port). The console's optional `logon` step registers its logon task and Start-menu shortcut on the stored port (`{port}` in its argv; 8790 until a `setup` stores one), so a second checkout runs `.\setup.cmd --port 8791` once and stays on 8791. `N` must be from 1024 to 65535 (`register.ps1`'s range); anything else is refused and not stored, and a bad stored value (say, hand-edited) is ignored with a one-line note, using 8790, by the window and the `logon` step's `{port}` alike (`progress.stored_port`). After changing the port, run the `logon` step again: it moves this checkout's registration to the new port, replacing the old port's task and shortcut. A server still running on the old port (it may be serving this wizard) keeps running until it's closed or you log off; from the next logon only the new port's starts. Falls back to the terminal setup when it can't (not Windows, a missing program, a failed build, `console open` failing), or exits 1 without a terminal to prompt in, always after one line saying why. When `console open` fails and another program holds the port, that line names it, read-only (`cli/port_holder.py` asks PowerShell for the listener's and its parent's exe paths; nothing connects): `The setup window couldn't open: port 8790 is used by another checkout's console, <its folder>. Close it, or run .\setup.cmd --port <a free port>.` |
| `setup --no-ui` | Interactive in the terminal: intro, prerequisites, tool checklist, each tool's steps (required run and copy steps just run; the rest ask first), one confirmation of the permissions summary, wiring, checks, optional tour. Resumes where it stopped. |
| `setup <tool>` | Set up or redo one tool in the terminal. |
| `setup step <tool> <step>` | Run that one step in the terminal and stop: no "Install?" question first and no wiring after (nothing written to Claude Code's config). Ends with the step's result in words; exit 0 done or skipped, 1 failed, 2 unknown id, 3 still needs input. It saves only what the step changed (its status, any answer) onto the progress as it is when the step ends, so whatever the setup window recorded meanwhile stays; when nothing changed it writes nothing. The setup window's `Open a terminal` runs this for a step that takes a secret, so the secret stays in that window. |
| `setup auto [tools]` | Run the automatic steps of every pick (or of the named tools, if picked) in one go, asking nothing: a step is automatic when it's a required `run` or `copy` step that isn't a terminal step or a browser sign-in (`Step.is_automatic`). Tools go in registry order; in each, done or skipped steps and every optional step are passed over (optional run steps register scheduled tasks or build Docker images, so each waits for its own click), and the first required step that needs the owner, or fails, ends that tool (its later steps build on it) while the batch carries on with the next. Never writes Claude Code's config. Prints each step's live output, then `{"ran", "stopped": [{tool, step, title, reason}], "messages"}`; exit 0 every pick's required steps done (or nothing is picked), 1 a step failed, 2 an unknown id or none of the named tools picked and runnable here ("Nothing ran", never "done"), 3 a step needs the owner. The setup window's `Save picks and install` and `Run the automatic steps` run this. Each step's status is saved onto the progress as it is when the step ends, so a `setup step` in a terminal meanwhile isn't undone. |
| `setup tour [topic]` | GUIDE.md one section at a time. |
| `setup status [--json]` | Each tool's status, platform label and any placeholders left in its config; a tool found already set up (below) reads `done`, and its line ends `found already set up`. `--json` gives each tool's health for the Tools list in the console's System tab: `active` (done and its verify check passes), `down` (done but the check fails or times out after 8 s) or `not_set_up` (whose words are empty when the tool was never picked, so the page reads `Not set up` once; else `skipped`, `setup started, not finished` or `a setup step failed`); checks run in parallel, in one round (`health.py`). Each row has `words`, `fix` and `command` (see Verify checks below), which the console's own health rows also have (those add `level` and `state`). Each row also has `wired`: the tool is done and its MCP servers are in `.mcp.json` and its hook modules in `.claude/settings.local.json` or `.claude/settings.json`, worked out by reading those files only (`wiring/present.py`). The page shows a done tool that isn't wired as "not added to Claude Code yet", never Active. And `detected`: setup has no record of the tool and found it already set up, so it is `active` with `setup_status` `done`, and its `words` are the check's plus ` · found already set up`. |
| `setup intro`, `setup tour --json` | The intro paragraph, and GUIDE.md's sections as JSON, for the setup window. |
| `setup doc <tool> <step>` | Prints the guide the registry names for that step (its `doc`), for the setup window, which shows it inline. Read-only, and it takes ids only, never a path: exit 2 for an unknown id or a registry `doc` that would leave the repo root (absolute, `..`, or a link out), 1 with one plain sentence when the step names no guide or the file isn't in this copy (the copytone skill ships only in the public edition). |
| `setup config [tool]` | Change a tool's settings: basic ones first, then any placeholder left, then (if you want) the advanced ones. `--list` prints them as JSON and `--set id=value` (repeatable) sets them without prompting. |
| `setup list`, `prereqs`, `choose`, `apply`, `mark`, `plan`, `wire --yes`, `verify`, `samples`, `config --list/--set` | Non-interactive commands for the setup skill (JSON out; exit 1 failed, 3 needs the user). `list` gives each tool's `group`, `cost`, steps (each with `automatic`) and status, `picked` (in progress `chosen`: the setup window opens on Welcome while nothing is picked, even though it built the console first), `wired` and `detected` (both as in `status --json`; a detected tool's status is `done` while its steps keep the status setup saved, none). `choose` records the picks and marks every other tool that already has a record skipped; a tool setup never touched, or only picked with no step run, is left without one, so picking one tool never hides the ones found already set up. `plan` prints one plain line per finished tool, `<name>: <what Claude may do without asking>` (its `consent` while it adds allow rules or hooks or has a done `unattended_claude` step; else `Claude can use its tools, but asks you each time.` for a server with nothing auto-approved, or `adds nothing to Claude Code.`; usage's line adds that it sets the status line when that step is done; `wiring/consent.py`), when no tool is finished, one `No tool is finished yet, so setup adds nothing.` line instead of any tool line, then the closing `Setup auto-approves nothing else. Your own permission settings, mode included, stay as they are.` line, one blank line, then the exact servers, rules and hooks; the setup window splits at that blank line. `verify` gives each tool's `ok`, `words`, `fix` and `command`, plus `output` (the check's last non-empty output line, stderr first) on a failed check without a summary, so the skill can reason about the error. |

## Found already set up

`.setup/progress.json` only knows what setup itself ran. Tools installed by hand, a lost `.setup/` folder, or a checkout copied to a machine that already has them would all read `not set up`, so for a tool the record says nothing about (never picked, or picked with no step run yet) the lists (`setup status`, `status --json`, `list` and the terminal setup's checklist, whose row reads `done; found already set up`) look at the machine instead (`detect.py`). The tool reads as set up, like a finished one, only when all of these hold:

- **Its `evidence` is there.** The registry lists local, gitignored paths only a machine where the tool was set up has: its venv (`tools/<tool>/.venv`), and for the job runner, which has none, its run-log folder (`tools/jobhunt/.logs`). A fresh clone has none of them, so nothing reads set up there and no check is even run (a `uv run --no-sync` check would leave an empty venv behind). A passing check alone proves nothing: the job runner's reads `set up, no run yet` from a checked-in script, and Agent rules and copytone have no check at all, so they have no `evidence` and are never found this way. A test holds that no evidence path is checked in.
- **It is in Claude Code's config** (its servers and hooks, as `wired`). `setup wire` adds only what the record lists, so a found tool that isn't there stays `not set up`: `Set up` leads to the wizard, which makes a real record and adds it.
- **Its verify check passes**, run as for a finished tool: required steps count as done, and an optional settings step whose config file was never made counts as skipped (the tool runs on its defaults), while a config file that is there is still scanned for placeholders. A check that fails or times out leaves the tool `not set up`, never `down`: `down` is for a tool the record says is finished.

The record wins wherever it says something: a skipped tool, or one with any step recorded (`started`, `failed`, `done`), reads as before. Finding is read-only: nothing is written to `progress.json` or any config, and `setup plan` and `setup wire` never count a found tool, so setup still grants only what was picked and run.

**What `wire` may take out.** Only what `wire` itself added. Every entry it adds to Claude Code's config goes into its ledger, `.setup/ledger.json` (`wiring/ledger.py`), exactly as written: each server in `.mcp.json`, each allow rule, each approved server name and each single hook (the hook, not its group) in `.claude/settings.local.json`, and the status line (which is only ever updated, never taken out). On a later run an entry is setup's only when the ledger lists it and the file still holds it as recorded. Those are swapped for the current plan's (`wiring/merge.py`), so a tool left out of the picks loses what setup added for it, and those entries leave the ledger too. One the plan still wants stays where it is, so a wire with nothing to add or take out writes nothing, whatever was added after setup's entries (Claude Code puts each approval in the same allow list). Every other entry stays exactly as it is, whatever `progress.json` says about its tool: a tool set up by hand keeps each server, rule and hook it has whether it reads found, started, failed or skipped. Where the plan wants an entry the config already has (a server of that name, a rule with that text, a hook for that module on that event, in `settings.local.json` or the checked-in `.claude/settings.json`), the one there is left as it is and setup doesn't take it over. In a hook group only setup's own hook goes; the group goes only when that leaves it empty. Once everything setup added is out, an empty container it made (such as `"hooks": {}` or `"allow": []`) can stay in the file. A missing or unreadable ledger means setup added nothing, so nothing is taken out. Entries setup wrote before the ledger existed aren't in it, so they count as yours and are left alone.

**Taking a found tool on.** The first time a result is written for one of a found tool's steps (`apply`, `mark`, `auto`, `step`, `config --set`, the terminal setup), its record starts as the one the detection assumed (required steps done, an optional settings step with no config skipped), with the step's real result on top (`detect.record_to_adopt`, `progress.adopt`). So re-running a step keeps the tool `done`, as for a finished one, and its row stops saying `found already set up`; if that step fails, the tool reads as a failed step. Whether the tool is found is read just before the step runs (an install makes the evidence itself); one that isn't found starts a plain record holding only that step. This only keeps the lists true. The entries the tool has in Claude Code's config were made by hand, so they aren't in the ledger and stay as they are, and the next `wire` adds only what the plan wants that isn't there yet. Picking a tool and un-picking it again (`choose`, the tool page's `Skip this tool`) leaves no record behind (`progress.unpick`), so a found tool goes on reading as found.

**Removing a tool.** Leave it out of `setup choose` and run `setup wire --yes`: that takes out what setup added for it. Setup can't remove what it didn't add, so entries made by hand are removed by hand: the tool's server in `.mcp.json` under `mcpServers`, and its `mcp__<server>` rules under `permissions.allow`, its name in `enabledMcpjsonServers` and its hooks under `hooks` in `.claude/settings.local.json` (or `.claude/settings.json`).

## Verify checks

A tool's `verify` in the registry is a cheap, read-only command run from the repo root (`verify.py`): the tool's own status command or a file read, never `--help` or an import (a test holds every tool with a program to this, and to having a registry `fix`). It never starts a daemon, opens a window or writes anything. The contract:

- **Pass or fail is the exit code**: 0 passes, anything else fails. A check that runs past its timeout (8 s for `status --json`) fails.
- **The last stdout line may be a summary**: one JSON object `{"words": "...", "fix": "...", "command": "..."}`. `words` (required, not blank) says what was found in one short line: a few words or one sentence. `fix` (a sentence) and `command` (a full command that runs as shown from the repo root) may be null or left out. One plain line each, at most 300 characters once stripped: a field with a line break or any other control character (a tab, a terminal escape) makes it no summary, since a copied multi-line command would run more than one command. Fields are stripped, and a blank `fix` or `command` counts as none. Any other last line, or JSON that isn't this shape, is not a summary. Earlier lines and stderr are ignored. Output is read as UTF-8 (the check runs with `PYTHONIOENCODING=utf-8`; bytes that aren't UTF-8 become the replacement character `�`, never an error).
- **Without a summary**, the words are plain: `installed` on a pass, `check failed (exit N)` on a fail. A check's own output is never the words, since for some tools it's a line of `--help` text. Only `setup verify` shows a failed check's last output line, as `output`.
- **The fix**: the summary's, else on a fail the tool's optional registry `fix` (one sentence), else none. A passing summary may carry a `fix` and `command` too (say "installed but not running"). A summary's command is the only command; the registry has none. Setup and the console only show or copy a `command`, never run it, so it must run as shown: a fix that needs a value filled in (say, a free port) goes in the `fix` words with `command` null.
- Setup's own failures use the same shape: placeholders left (fix and the `setup config` command), the program missing, the timeout (both take the registry `fix`).

The console's check is `console doctor --summary-json`: it exits 1 only on a fail row (attention rows alone pass) and then ends with the first fail row as the summary.

Each tool's check. The console's doctor and the checks added for this (contextmeter, browser, mail-digest, sessions, whiteboard, analysis-chamber, jobhunt, audiohub, mail) print a summary; brief, usage, vault, calendar and sleepmode don't, so they read `installed` on a pass:

| Tool | Check | Passes with |
|---|---|---|
| brief | `brief away status` | installed |
| usage | `usage show` | installed |
| contextmeter | `python -I -m contextmeter.check` (reads files only) | `ready, hands off at 75%; has run` or `hasn't run yet` |
| console | `console doctor --summary-json` | the doctor's words |
| audiohub | `audiohub check` (a token-file and loopback-port look, starts nothing) | `Voice hub is running`, or `Installed, but the voice hub isn't running` with a start command |
| browser | `browser-tool --check` (loads the config only) | `config OK, N sites allowed` |
| vault | `vault list` (decrypts nothing) | installed |
| mail | `mail check` (reads the saved sign-ins and client file, no network; can't see a sign-in Google revoked or expired) | `N accounts saved (not tested against Google)`; fails with a fix when none, one is unreadable or the client file is bad |
| calendar | `calendar agenda --days 1` | installed |
| mail-digest | `mail-digest status` (reads the state file) | `last run worked (<time>)`, or `set up, no run yet` |
| sessions | `sessions check` | `N repos found; daemon running`, or `daemon not running (starts on first use)` |
| whiteboard | `whiteboard status` | `running`, or `installed, not running (a board call starts it)` |
| analysis-chamber | `analysis-chamber check` | `running, N runs`; down with `installed, daemon not running` or `kit not built` |
| sleepmode | `sleepmode status` | installed |
| jobhunt | `tools/jobhunt/status.ps1` (reads the newest run log) | `last run finished (<time>)`, `a run is going`, or `set up, no run yet` |

A daemon that starts on first use (sessions, whiteboard) passes while it isn't running; one that must already run (analysis-chamber) is down. Either way an installed tool reads differently from one that isn't: a check that can't start fails with `check failed (exit N)` and the registry's fix. agents and copytone run nothing, so they have no check (`nothing to check`).

## What it writes

- `.setup/progress.json`: chosen tools, each step's status and the answers registry steps fill in (`email`, and `port`, the console's) (gitignored).
- With the console's `logon` step: a per-user logon task and a Start-menu shortcut, both `Signal console (<checkout folder>, port <port>)` (`tools/console/register.ps1`; `unregister.ps1` removes them).
- `.mcp.json`: the chosen tools' servers, copied from `.mcp.example.json`, beside any servers and other keys you added yourself. Whatever setup didn't add stays as it is here and in the settings file, a server with a chosen tool's name included (see What `wire` may take out, above).
- `.claude/settings.local.json`: the chosen tools' allow rules, `enabledMcpjsonServers` and hooks, merged with your own entries. It never sets a permission mode.
- `~/.claude/settings.json` `statusLine`, only if you accept usage's status line and have no other one; one setup wrote earlier is updated, and any other is kept, usage's own module or not. It is never removed.
- `.setup/ledger.json`: the ledger of every entry `wire` added to those files (gitignored). `wire` takes out or replaces nothing that isn't in it. With a plan that adds nothing and nothing in the ledger, `wire` leaves all of them untouched.
- `.setup/backups/` (`mcp.json`, `settings.local.json`, `user-settings.json`): each of those three files as it was the last time setup went to replace it. If any file it's about to write isn't a JSON object, setup refuses before writing any (one line, exit 1, all three untouched). It writes nothing when the merge changes nothing. Otherwise it writes the new file to a temp file, re-reads the old one, and only if it's unchanged since the first read backs it up and replaces it in one step, so a crash can't leave half a file; if it changed (or Windows says another program has it open), setup starts over once, then refuses (`wiring/json_file.py`).
- `.env` from `.env.example` when missing, and the mail and calendar address constants (`SELF_ADDRESS`, `OWNER_EMAIL`), which stay source constants so nothing at runtime can redirect self-sends.
- copytone samples in `.claude/skills/copytone/samples/` (gitignored). That folder is the public edition's copytone skill; the private edition marks the copytone steps skipped, so the samples step doesn't run there.
- Each tool's settings (see below): the gitignored config copied from its example, or a tracked file such as a `schedule.psd1`, edited a line at a time so your comments stay.

## Settings and placeholders

The `agents` entry in the registry is Signal's own rules: its one setting, `context-handoff-percent` (30 to 90, default 75), is the number in AGENTS.md section 4. AGENTS.md is a tracked file whose value sits in prose, so it's marked `<!-- setting:context-handoff-percent -->75<!-- /setting -->` and read by `formats/md_marked.py` (picked by file name; only marked values count).

`src/signal_setup/data/settings/<tool>.json` lists a tool's config files (with the example each is copied from, and a group: "" for the main settings step, `checker` for mail-digest's optional assignment checker) and its settings: key, file, type (`str`, `int`, `float`, `bool` (yes/no in Markdown files), `list`, `times`), `basic` or `advanced`, description, hint, optional `min`/`max` for numbers, and `rerun` (a step to run again after a change, e.g. re-registering a scheduled task). Defaults are the example files' values.

The examples ship placeholder values (reserved `example.edu`/`.com`/`.org` hosts, `YOUR_...`, `<...>`, `TODO(...)`). A `settings` step is done only when none is left in its files, setup refuses a placeholder as a new value, and `status` and `verify` list any left. A placeholder the schema doesn't name (say a `TODO(owner)` line in the jobhunt profile) is asked for too, with the id `<file>:<key>`. In a Markdown file (the jobhunt runbook and profile) a `- Label: value` line can be prose, so there an `<angle-bracket>` slot counts only when the value is nothing but slots (`<a number>`); a slot inside a sentence is the run's own template syntax (`from <old date>`). The other markers count anywhere (`tests/test_settings.py` holds this).

## Layout

- `settings/`: schemas, the TOML/psd1/Markdown line writers (`formats/`), typed values, the placeholder scan, and the store.
- `registry.py`, `platforms.py`, `progress.py` (a tool is done when its required steps are; one with only optional steps once one of them is done or skipped), `prereqs.py`, `verify.py`, `detect.py` (tools found already set up, read-only, and the record one is taken on with), `health.py` (the states of the Tools list in the console's System tab), `intro.py`, `terminal.py` (prompts)
- `steps/`: runs one step (`settings_step.py` is the settings prompts). `wiring/`: plan, merge and write Claude Code config (`json_file.py` is the safe read-merge-write; `ledger.py` is the record of what `wire` added and `merge.py` the merges that go by it; `consent.py` is each tool's plain line for the consent page), plus the small file edits.
- `samples/`: copytone sample import (files, paste, sent mail). `ui/`: checklist, the interactive flow (and `setup step`'s one step), the tour.
- `wiring/present.py` reads (never writes) which done tools are already in Claude Code's config.
- `cli/`: `main.py` (entry point), `agent.py` (the skill's and the window's commands), `auto.py` (`setup auto`), `config.py` (`setup config`), `doc.py` (`setup doc`), `ui_launch.py` (`setup ui`), `port_holder.py` (who holds the console's port, for `setup ui`'s fallback line).
