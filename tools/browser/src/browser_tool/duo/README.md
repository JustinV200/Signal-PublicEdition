# browser_tool.duo

Duo two-factor prompts, which only the owner answers, on their phone. This package spots them in every tab, gives the owner a spoken heads-up through the audiohub voice hub, queues a notice for the model, relays Duo's Verified Push code on sites the owner listed (read only), provides the live check behind the acting tools' lockout, and waits (read only) for a tab to leave Duo.

## Public API (`from browser_tool.duo import ...`)

- `is_duo_url(url)` is True for a network URL on `duosecurity.com` or any subdomain of it (e.g. `api-1a2b3c4d.duosecurity.com`).
  - Only the parsed hostname counts, case-insensitive, with a trailing dot stripped. `evil-duosecurity.com`, `duosecurity.com.evil.com` and a Duo host in a path or query don't match.
  - `blob:` and `filesystem:` URLs are checked by their inner URL.
  - Default-deny: a network URL whose host can't be parsed counts as Duo. URLs with no host (`about:`, `data:`, `""`) don't.
- `DuoWatch(settings: DuoSettings, clock=time.monotonic)`, owned by `BrowserSession` as `session.duo`:
  - `is_in_duo(page)` is the lockout check (`browser_tool.actions.guards.ensure_not_in_duo`). It is True while any frame of the tab (main frame or iframe, nested ones too) passes `is_duo_url`, reading the frames at call time, so it never depends on event bookkeeping. A popup that a tab in Duo opened also counts, while the popup is on a page with no host: an `about:blank` or `blob:null` popup can be scripted by Duo itself.
  - `watch(context)` follows every open and future tab. It re-checks a tab on each `framenavigated` and `framedetached` event, notes its main-frame navigation requests (to vet the site, see below), so a prompt is noticed as soon as it loads, even between tool calls, and it marks popups opened from a tab in Duo.
  - On a new prompt it queues one notice for the model, naming the tab's index in `tabs()`, and, when `voice_heads_up` is on, posts one `HubNote` through `signal_hub_notify.Notifier`: source `browser`, priority `urgent`, text "Duo push for <site>, approve on your phone."
  - Only the latest pending notice per tab is kept, so a page that keeps re-adding a Duo iframe can't pile them up.
  - On sites in `[duo] code_relay_sites` it then reads the prompt's Verified Push code and relays it once (see "Verification codes" below).
  - `async take_notices()` returns and clears the queued notices, each ending with one fixed line on its prompt's voice heads-up (`ping_line`, below), waiting up to 2 s for a delivery still in flight. `ToolRunner` appends them to the next tool result, success or error, after the scrub and after the action's text, so outside `<untrusted_page_content>`.
  - `async ping_outcome(page, wait_s=8.5)` is the outcome of the tab's latest heads-up: a `signal_hub_notify.Delivery` (`SPOKEN`, `DROPPED` with its reason, `NO_HUB`, `FAILED`), a `PingSkip` (`RATE_LIMITED`, `VOICE_OFF`, or `STILL_SENDING` once `wait_s` runs out), or None when no prompt was announced there. `wait_for_duo` reads it.
  - `drain()` waits for running code relays, then for posted notes (tests).
  - Raises `ValueError` on a malformed `code_relay_sites` pattern, like `ActionContext.create` does for `[policy]`.
- `DUO_LOCKOUT_MESSAGE` is the refusal the acting tools return.
- `ping_line(outcome, min_interval_s)` is the fixed voice line: `voice ping: spoken`, `voice ping dropped: the owner is asleep` (or away; the reason is one of `signal_hub_notify.DROP_REASONS`, never hub text), `voice hub not running`, `voice ping skipped: one was sent under 60 s ago`, `voice ping failed (...)`, `voice ping off (...)`, `voice ping: still sending` or `no voice ping for this prompt`.
- `wait_until_off_duo(page, timeout_s, is_waiting, clock=time.monotonic) -> WaitOutcome` (`DONE`, `TIMEOUT`, `CLOSED`) waits until `is_waiting(page)` is False. It only reads frame URLs, woken by `framenavigated`, `framedetached` and `close`, with a 1 s poll as a fallback; it never clicks, types or evaluates. `wait_for_duo` passes `DuoWatch.is_in_duo`; visit mode passes "on the login host or Duo".
- `wait_for_settle(page, quiet_s=1, max_s=10)` waits, read only, for the main frame to load and then stay put for `quiet_s`, so `wait_for_duo` reports the page a login's hand-off redirects end on. (navigate, back, click and press_key settle through `actions.navigation.NavigationWatch` instead, only when a main-frame navigation happened.)
- `TabDuoState(same_prompt_window_s)` is the pure once-per-prompt rule; `update(main_url, frame_urls, now)` returns True when a new prompt starts.
- `TabDuoState.vet_duo_navigation(request)` forgets the site unless a top-level navigation request to Duo came straight from it: every redirect hop on Duo or on the site, and the chain's first request carrying a `Referer` on the site (or on Duo, once the tab's top-level page is on Duo).
- `heads_up_note(site, job_label=None)`, `code_note(site, code, job_label=None)` and `model_notice(site, tab_index, code=None, *, is_code_withheld=False)` are the wording. All show `site` only if it is made of `[a-z0-9.-]`, and "a login" otherwise, unless the owner named the host in `[duo] site_names` (exact hostname to a name of letters, digits, spaces, dots and hyphens, at most 40 characters, checked by the loader): then that name (`shown_site(site, site_names)`). Only the tab's own vetted site is looked up, never a page-supplied parameter such as CAS's `service=`. A voice note in a docker job starts with its label ("docker job 1a2b3c: Duo push for ..."); `DuoWatch(..., job_label=)` reads it from the session's backend.

## Once per prompt

- A tab is in a prompt while any of its frames is on a Duo host. Duo-to-Duo redirect hops never leave Duo, so a whole redirect chain is one prompt.
- A tab that leaves Duo and comes back within `[duo] same_prompt_window_s` (10 s) is bouncing within the same prompt: nothing new is sent. After that, a new prompt gets a new notice and heads-up.
- `<site>` is the tab's last non-Duo top-level hostname, so a top-level redirect to Duo still names the site being logged in to, and an embedded Duo iframe names the page around it. A tab that opened straight on Duo says "a login", and so does a top-level page with no host (`about:blank`, `blob:`, `data:`). Such a page can be put in a tab by another site (an opener can set the tab's location), so it never borrows the name of the site the tab showed before (earlier versions kept that name). Redirect hops never commit, so `DuoWatch` also follows each tab's main-frame navigation requests. A top-level navigation to Duo whose redirect chain passes through any host but Duo and the site (site, then `evil.example`, then a 302 to the attacker's Duo) forgets the site. So does one the site's own page didn't start, and so does a prompt that starts on a top-level Duo page with no matching request (a back/forward-cache restore).
- **The `Referer` rule.** A tab showing the site can be sent to Duo by something else: the page that opened it, a popup it opened (`window.opener`) or any page targeting its window name, a third-party frame setting `top.location`, or Claude's own `navigate`. So the first request of the chain to Duo must carry a `Referer` whose host is exactly the site; a missing or unreadable one fails closed (Claude's `navigate` sends none, and a page can choose to send none). A `Referer` on Duo counts only while the tab's top-level page is already on Duo, for Duo's own hops inside a prompt that was vetted on the way in, so a Duo iframe can't vouch for moving the whole tab. Only the first request's `Referer` is read: it names the page that started the navigation, and a redirect's `Referrer-Policy` can strip it from later hops. It is read from Playwright's synchronous `request.headers`, so the vetting is done before the page commits and the prompt is announced. Only the hostname is used, never a path, query or page text, and only if it is plain `[a-z0-9.-]`. The site picks its own hostname, so the name can still spell words, but it can't carry markup.

## Voice notes are rate-limited

Voice heads-ups are at least `[duo] min_heads_up_interval_s` (60 s) apart, across all tabs. Without that, a page could embed a Duo iframe again and again to have the owner told "approve on your phone" every few seconds, priming them to approve an attacker's push. A skipped note is logged. The lockout and the model's notice are not rate-limited, so a genuine second prompt inside the interval still reaches the model, which can push the owner's phone.

The one code note per prompt (below) skips that global interval. Its relay starts only after that prompt's heads-up was posted or rate-limited, so it can never be the first note about a prompt or a second code for it. Code relays are held to the same interval per site instead, across tabs, voice note and model notice alike: at most one "type it in Duo Mobile and approve" per site per `min_heads_up_interval_s`, so the known gaps below can't make it come often. A capped relay is logged, and its notice says the prompt showed a code that wasn't relayed (rate limit) and asks for no push.

## Verification codes (read only)

With Duo Verified Push, the prompt shows a short number that the owner types into Duo Mobile before approving. Reading it saves the owner a look at the PC. The tool only reads text the Duo frame displays; the lockout (no clicks or typing in Duo) is unchanged.

- **Top-level Duo only.** Only a tab whose top-level page is on Duo is read: the Universal Prompt, which Duo doesn't allow in an iframe (iframe delivery ended in March 2024 for most apps). A Duo frame embedded by any page is never read, because that page is Duo's parent, gets Duo's result back, and may not be the site being logged in to.
- **Allowlist, off by default.** The prompt's `<site>` (above, vetted against the redirect chain and `Referer`) must match `[duo] code_relay_sites`, host patterns matched like `[policy]` (`HostPolicy`). The default is empty. Reason: someone who has the owner's password could start a real Duo login and show the real Duo prompt from their own page. Reading that code out would prime the owner to approve them.
  - Prefer exact login hosts (`sso.example.edu`). A wildcard such as `*.example.edu` trusts every subdomain, including any one an attacker can get content or an open redirect onto.
  - A tab that opened straight on Duo, or reached it from a page with no host (`blob:`, `about:`, `data:`), has no site and is never read.
- **Not through history.** A Duo page reached by back/forward isn't read: history replays the original request, so the chain check can't tell, but the document's Navigation Timing type (`back_forward`) can. A type that can't be read counts as history.
- **Checked throughout.** The top-level page, the site and the allowlist are judged when the relay starts, on every poll, and again right before the code is handed on; the reason is logged when the tab stops qualifying. The code must also come from the document the history check read: the top-level document's `performance.timeOrigin` is read before the code and again after that check, and a change means no code.
- **Polling.** A new prompt starts a background task (`CodeRelay`) that reads the tab's Duo frames every `code_poll_interval_s` (1 s) for up to `code_relay_timeout_s` (45 s). It stops on the first code, when the tab stops qualifying (above), when it leaves Duo (`DuoWatch` stops it on the frame event) or closes, or when a new prompt in the tab replaces it. Nothing waits on it, and its failures are logged (type and frames only), never raised. Duo's "send another push" inside the same prompt shows a new code, which isn't relayed: the relay has already stopped.
- **The heuristic (`code_reader`), which fails closed:**
  - Only the top-level Duo page and frames on a readable Duo host whose every ancestor is one too are read. Non-Duo frames inside the prompt, `blob:` frames and Duo-ish URLs whose host can't be parsed are ignored, whatever they show.
  - A candidate is a visible text node that is exactly 3 to 6 ASCII digits, near Duo's code wording: "code", "enter" or "verification" in the node's element or one of its 3 ancestors. Each counts through its `aria-label` and `aria-labelledby` text, and through its own text while that is at most 300 characters.
  - Exactly one distinct candidate across the tab's Duo frames is the code. None, two or more, a frame that can't be read, or a reply that isn't a short list of digit strings means no code.
- **Delivery, once per prompt, once per site per interval.** The tab's pending notice is replaced by one that also gives the code and asks the model to include it in any PushNotification. With `voice_heads_up` on, the hub hears an urgent "Duo code for <site>: 4 8 2. Type it in Duo Mobile and approve.", digits spaced so the voice reads them one by one. Within `min_heads_up_interval_s` of the site's last relay, neither happens (above). The code is never logged by this package (the hub client logs a dropped note's text when the hub is down).

## Never blocks, never fails loudly

The note is posted in a background task with connect and reply timeouts (see `packages/hubnotify`); its outcome is kept per tab for the notice's ping line and `wait_for_duo`. Heads-ups and code notes are urgent and marked `ring_through` (messages.py), so audiohub speaks them even while the owner is asleep or away; the owner may still not answer, and `wait_for_duo` then times out cleanly. A note a hub still drops unspoken (one that doesn't honour ring-through) reads "voice ping dropped": the hub's own rule decides that, not this package. The token is read from `hub_token_file` (default `tools/audiohub/.cache/ipc-token`) at each delivery. A missing file, a refused connection or a timeout is logged and skipped, and no error reaches the model. An exception in an event handler is logged (type and stack frames, never the message, which can hold URLs) and swallowed, because it would otherwise break Playwright's event dispatch. The lockout still holds, since it reads frames live.

## Known gaps

- TODO: a Duo iframe isn't locked until its Duo URL commits. While it loads, the frame still reports its old URL (`about:blank`), so acting tools aren't refused for that moment. Nothing from Duo is on screen yet, but a click could land as Duo appears. Closing this needs the iframe element's `src` checked as well as the frame URL.
- TODO: the lockout covers the current tab only. A Duo popup doesn't lock the tab that opened it. Claude can't act inside the popup without `switch_tab` to it, which then locks. Locking every tab while any tab is in Duo would close this, at the cost of pausing unrelated tabs.
- `click`, `type_text`, `select_option` and `press_key` re-check right before touching the page, but a navigation the browser has committed and whose event hasn't reached the tool yet isn't seen. `fill_login` doesn't re-check after the vault's own dialog; the vault's origin re-check on its element handles stops a fill on a tab that moved, but not one on a page that added a Duo iframe meanwhile (that fill only touches the site's own login fields).
- A popup opened with `noopener` has no opener, so it is judged only by its own URL.
- An open redirect on a `code_relay_sites` site itself can still put a Duo prompt under its name. A client-side one (JavaScript or `<meta>` sending the tab to a Duo URL taken from the query or fragment) starts the navigation from the site's own page, so it carries the site's `Referer` and passes; its code is relayed at most once per site per `min_heads_up_interval_s` (above). A server-side one (a 302 from the site) is caught unless a page on the site links to it, because the chain's first request then carries the other page's `Referer`, or none. Prefer exact login hosts, which have little room for either.
- The `Referer` rule wasn't checked against a live Duo login, and it fails closed wherever no `Referer` is sent, so no code is relayed: a login page with a `no-referrer` policy, a site Claude navigated to that redirects straight to Duo before any of its pages commit, and Duo's own client-side hops inside a prompt if Duo's pages send no `Referer` (a fake Duo page with `Referrer-Policy: no-referrer` does just that). `Sec-Fetch-Site` could vouch for Duo's hops, but a local probe found it in neither `request.headers` nor `all_headers()` on this tool's requests, all of which are routed (`session/request_guard.py`), so it isn't used.
- With the back/forward cache on, a restore makes no request and is caught by the missing-request rule (above). Playwright's Edge runs with it off, so history replays a request, which the Navigation Timing check catches instead.
- A site that hands off to Duo through another of its own hosts (`my.example.edu`, then `cas.example.edu`, then Duo, without the middle page committing) fails the chain check, so its code isn't relayed. The prompt reads "a login".
- The code heuristic was written without a live Verified Push prompt to look at. If Duo splits the digits across elements, spaces them inside one text node, or uses a shadow root, nothing is relayed (it fails closed). A tab that bounces out of Duo and back within `same_prompt_window_s` stops its relay and, being the same prompt, doesn't start a new one.

## Files

- `hosts.py`: `is_duo_url`, `is_duo_host` (`host_of` lives in `browser_tool.policy`).
- `prompt_state.py`: `TabDuoState`, the once-per-prompt rule and the redirect-chain and `Referer` check on the prompt's site.
- `messages.py`: the voice notes, the model notice and the lockout refusal.
- `code_reader.py`: `read_verification_code`, the in-frame heuristic.
- `code_relay.py`: `CodeRelay`, the top-level-Duo, site and history rules and the per-tab polling task.
- `failure_log.py`: `log_failure`, type-and-frames logging for handlers and tasks.
- `pings.py`: `HeadsUpPings` (the notifier, the heads-up rate limit and each tab's latest outcome), `PingSkip`, `recent_gap_s`.
- `wait.py`: `wait_until_off_duo` and `wait_for_settle`, the read-only waits.
- `watcher.py`: `DuoWatch` (Playwright events and navigation requests, popups, the notice queue, the per-site code cap, the code relay, `is_in_duo`).

## Dependencies

`playwright` (types and events), `signal_hub_notify` (`packages/hubnotify`), and browser_tool `config` (`DuoSettings`, `resolve_tool_path`) and `policy` (URL scheme helpers, `HostPolicy` for the code relay allowlist).
