# Tells to avoid

Things that make text or code read as generic instead of the user's own. Every item is a hard rule unless `voice-profile.md` shows the writer doing it, in which case the profile wins.

## Prose

Punctuation and typography
- No em dashes anywhere. No en dashes or double hyphens standing in for them. Use a comma, a period, or rewrite the sentence.
- No colon setting up a reveal ("Here's the thing:", "The result:").
- No semicolons unless the profile shows them.
- No bold or italics for emphasis inside prose.
- No emoji. No arrows. No checkmarks.
- Straight quotes unless the samples show curly ones (Word docs often do).

Words and phrases
- Banned words: delve, tapestry, landscape (figurative), leverage, robust, seamless, crucial, pivotal, navigate (figurative), foster, underscore, testament, multifaceted, nuanced, realm, embark, journey (figurative), harness, utilize, vibrant, comprehensive, cutting-edge, game-changer, holistic, paradigm, synergy, streamline, elevate, empower, unlock, unpack, resonate, intricate, myriad, plethora, showcase, highlight (verb), facilitate, ensure, enhance, optimal, key (as in "key insight"), additionally, furthermore, moreover, notably, importantly, ultimately, overall, essentially, arguably, indeed.
- Banned openers: "In today's world", "In today's fast-paced", "Throughout history", "Since the dawn of", "It is important to note", "It's worth noting", "Great question", "Certainly", "Absolutely", and restating the prompt back before answering it.
- Banned closers: "In conclusion", "In summary", "To sum up", "Overall,", "At the end of the day", "Ultimately", a last paragraph that repeats the body, ending on a question, ending on a call to action, ending on a hopeful note about the future.
- No "It's not X, it's Y", "not just X but Y", "not only X but also Y" framing.
- No "This ensures that", "This allows for", "This highlights", "This demonstrates", "serves as", "plays a crucial role", "a wide range of", "a variety of", "in order to" (just "to").
- No rhetorical question followed by its own answer.
- No "Let's" (dive in, explore, break this down, take a look).
- No stacked hedges ("may potentially", "could possibly", "it seems that it might").

Rhythm and structure
- No groups of three for their own sake ("fast, reliable, and secure"). Two or four is fine if that is what there is.
- No run of sentences with the same shape. Vary length. Let one be short. Let one ramble if the samples do.
- No paragraphs where every sentence starts with the same word or pattern.
- No headers, bullets, or numbered lists in a letter, post, or email unless the samples do it or the task asks for it.
- No topic sentence, three supports, wrap-up sentence formula in every paragraph.
- No summary paragraph at the end. Most people just stop.
- No "First... Second... Finally" scaffolding unless the profile shows it.
- Do not define terms the reader obviously knows. Do not explain the obvious step.
- Do not cite or attribute more than the samples do.
- Do not use textbook or docs jargon the writer wouldn't, or paraphrase definitions.
- Do not be more balanced than the samples. If the writer takes a side, take it.

Polish
- Do not fix things the samples get wrong consistently. Match the polish level, not the ideal.
- Do not smooth every transition. Two paragraphs can just sit next to each other.
- Do not make every paragraph the same length.
- Do not add a title unless asked or the samples have one.

## Code

When writing code in the user's style, match the conventions visible in their code samples: naming, comment density, file layout and structure. Do not lower quality to do it. Keep correctness, input validation, type hints and tests wherever the codebase uses them.

- No narration comments ("# loop through the list", "// return the result") and no "Step 1:" scaffolding unless the samples do it.
- Match the samples' formatting, string style and constructs (loops vs comprehensions and so on).
- Output messages are plain. No emoji, no box drawing.
- Do not add features the task didn't ask for.
